# Security Policy

JinDun Sentinel is an open-source project. Security reports are handled privately
until a fix is available.

## Reporting a vulnerability

**Do not open a public issue for a security vulnerability.** A public issue is
visible immediately and to everyone, and it gives an attacker a head start.

Use GitHub's private vulnerability reporting:

1. Open the repository's **Security** tab.
2. Select **Report a vulnerability**.
3. Describe the issue as precisely as you can and submit the report.

The report opens a private security advisory that only the maintainers can see, and
it gives you a private channel for the discussion. If private reporting is not
available in your copy of the repository, open an ordinary issue **that contains no
exploit details, no proof-of-concept code and no live endpoint**, and ask the
maintainers for a private channel in that issue.

Please include, where it helps:

- what an attacker can do, and what they need in order to do it;
- the affected file, endpoint or configuration, with the version or commit;
- the steps to reproduce it;
- the impact you believe it has.

### What to expect

You will get an acknowledgement of the report, an assessment of the impact, and a
decision on whether the project will issue a fix, an advisory, or both. If the report
is accepted, you will be asked whether you want to be credited in the advisory and in
`CHANGELOG.md`. If it is declined, you will be told why.

Please give the maintainers a reasonable amount of time to publish a fix before
disclosing the issue publicly.

## Disclosure timeline

| stage | target |
| --- | --- |
| acknowledgement of the report | 3 working days |
| initial assessment and severity rating | 10 working days |
| fix or mitigation released | 30 working days from the assessment, sooner for critical issues |
| public advisory and release note | on release of the fix, coordinated with the reporter |
| supported versions patched | the latest release, and the previous release when the fix is a breaking change |

These are targets rather than guarantees, but they are the ones the project commits
to. If a target cannot be met, the maintainers will say so in the advisory thread
before the deadline passes, with a reason and a revised date.

## Supported versions

The project is pre-1.0. Fixes are released on the `main` branch and published as a
new version. Security fixes are **not** backported to earlier releases.

| version | supported |
| --- | --- |
| `main` | yes |
| latest release | yes |
| earlier releases | no |

## What is in scope

In scope — anything that could compromise a deployment of this project:

| area | why |
| --- | --- |
| The API server (`packages/api`) | it serves the published artefacts over HTTP; an attacker who can reach it may read data, exhaust resources or reach a path it should not |
| The pipeline and its adapters (`packages/pipeline`) | a malicious or malformed upstream payload that the adapters mishandle, a path traversal in the snapshot store, or a code path that executes something it should not |
| The snapshot and artefact stores | the snapshot store writes attacker-influenced content to disk; the API reads artefacts back and serves them |
| The locale catalogue handling | the catalogue is loaded from disk and rendered; the message endpoint reflects its content back to the caller |
| The web front end (`packages/web`) | cross-site scripting, an unsafe `v-html` use, a prototype-pollution path, or a dependency with a known exploitable advisory |
| The build and dependency configuration | a compromised lock file, an unpinned download, or a workflow that executes untrusted input with credentials |

## What is out of scope

Out of scope — these are not vulnerabilities in this project:

| report | why |
| --- | --- |
| The *data* being wrong | a stale series, a revised official figure, an index that disagrees with an external source, a quality gate that passes data it should reject | 
| A statistical finding | a methodology question, a disagreement with a published number, a request for a different estimator, or a claim that an alert rule fires too often |
| The upstream services themselves | a defect in the ECB, BIS, Bank of Japan or FSB service, or in the `akshare` package |
| Denial of service by flooding the API | the API is a read-only view over local artefacts; sending it a very large number of requests is an operational problem, not a vulnerability |
| Missing hardening that has no attack path | a missing header on a response, the absence of authentication on an endpoint that only serves published statistics, or the absence of a rate limiter |
| Vulnerabilities in a dependency with no reachable path through this project's code | report these to the dependency's own maintainers first; they become in scope here only once a reachable path exists |
| Reports generated by an automated scanner without a demonstrated impact | please include the reachability argument |
| Anything found through attacking a system that is not operated by the project | third-party infrastructure |

### A note on the API and on published statistics

The API is designed to be read-only and to serve artefacts that the pipeline has
already published. It has no authentication layer, because it exposes nothing that
is not already published and it is meant to be reachable by a public dashboard. If a
deployment exposes it beyond a trusted network, the operator is responsible for the
network placement — the project does not treat the absence of authentication as a
vulnerability.

## Hardening notes for operators

These are the properties that matter when deploying the project. They are listed so
that an operator can check them, not because the project considers their absence a
vulnerability.

| property | value |
| --- | --- |
| default browser origins allowed by CORS | `http://localhost:5173,http://127.0.0.1:5173` — set `JINDUN_CORS_ORIGINS` to narrow or widen it |
| HTTP methods accepted | `GET` and `OPTIONS` only |
| artefact directory the API reads | `JINDUN_RUNS_DIR`, default the repository's `data/runs` |
| locale catalogue the API reads | `JINDUN_LOCALE_DIR`, default the empty `packages/pipeline/locales` in a source checkout |
| user agent sent to the external services | `jindun-sentinel/0.1` |
| outbound request timeout | 30 s, with 3 attempts and exponential backoff |
| write access | the pipeline writes only under the snapshot directory and the run output directory; the API never writes |

## Attribution

Reporters are credited in the security advisory and in `CHANGELOG.md` unless they ask
not to be. The project follows the same expectations as the
[Contributor Covenant](CODE_OF_CONDUCT.md): no harassment of reporters, and no public
disclosure of an unfixed vulnerability without an agreed timeline.
